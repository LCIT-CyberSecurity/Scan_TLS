# DNS lookalike monitoring architecture

## Components and flow

The feature is isolated in `services/dns_discovery/lookalike.py`. The catalog API stores per-domain configuration in `dns_lookalike_monitors`; a disabled row has no schedule. An explicitly enabled monitor registers a `dns_discovery` task with the existing `ScanSchedule` and scheduler. The scheduler revalidates owner role, monitor state and domain before queuing a `DnsDiscovery`. The existing DNS worker checks monitor state again before making queries. Results are stored as per-run snapshots in `DnsDiscovery.result`; no other inventory model is changed.

```text
Admin UI → catalog API → monitor + existing DNS schedule
                                 ↓ due/manual
                         DNS worker revalidation
                                 ↓
                 bounded candidates → DNS / optional CT
                                 ↓
                    immutable run snapshot + diff
                                 ↓
                         opt-in notification
```

## Candidate generation and library choice

Candidate variants are generated by a small deterministic Python implementation with one edit per result rather than a broad fuzzy-domain dependency that can create large, hard-to-review sets. The `idna` package is used in strict IDNA2008/STD3 mode for Unicode validation and punycode conversion. This keeps the dependency surface narrow while using a maintained implementation of the protocol.

## Security and limits

- Monitoring, CT and alerts default to false; no candidate generation or external request occurs until an enabled run is dispatched.
- Public-domain validation and IDNA normalization are applied before persistence and generation. Configured names are not sent to CT unless explicitly opted in and the administrator's current setting allows it.
- DNS resolution uses the worker resolver and bounded concurrency/timeouts; candidates are capped at 200. CT is capped at five candidate requests per run, has bounded responses and does not follow redirects through the existing DNS discovery provider.
- The scheduler and worker each recheck authorization and enabled state. The DNS schedule remains the only scheduler.
- Results distinguish DNS and CT evidence; absence is `not_observed`, not deletion. Wildcard responses are marked; no result asserts malicious intent.
- Notification preferences add `dns_lookalike`; alerts require both monitor opt-in and the user's explicit event preference, and only newly observed or changed candidates are sent relative to the preceding snapshot.
- RDAP is intentionally unimplemented: there is no configured provider/allowlist or validated service contract in this deployment. The result remains `not_checked`.

## Schema and migration

Migration `0022_dns_lookalike_monitoring` adds an isolated monitor table with an explicit false server default, soft-delete timestamp, owner, bounded JSON options and a nullable foreign key to the existing schedule. Existing DNS discoveries and schedules are unchanged. The migration must run using the normal WebUI upgrade procedure documented in [installation](../admin/install.md). Rollback drops only the new table; do not downgrade after creating production monitors unless their configuration/history may be discarded.

## Validation status

Unit tests cover deterministic candidate generation, caps, TLD validation, exclusions, IDNA encoding, public-domain rejection, DNS/CT/RDAP injected observation states, wildcard detection and the rule that candidates are never labelled malicious. API, notification delivery and scheduler integration require the Docker Sandbox and remain unverified until that environment is available. RDAP remains an explicit limitation.
